# 执行稳定性与结构审计（2026-11-10）

审计基线：`fdb0ac5`，0.18.0 草稿分支；主分支尚未包含这批功能。

## 判断

项目有明确的生命周期、索引、存储、备份和诊断分层，也有不可变对象、
预览摘要、提交前置条件和恢复测试。按本次检查，不能简单归为失控的“屎山”。
但它已经存在明显的模块膨胀和内部 API 耦合；继续把新职责塞入大文件会使维护成本上升。
测试基线全部通过仍漏掉了下列异常输入和边界条件，因此不能用通过率代替稳定性判断。

## 已复现并修复

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| 隔离包复检复用了导出扫描器 | 额外的嵌套 Skill、缓存目录被忽略，修改后的隔离包仍能通过校验 | 导出过滤与完整目录复检分离，安装和重复导入共用严格校验 |
| inbox 映射缺少用途边界 | 可将下载包写入 VCS、管理状态或 Skill 自动发现目录 | 共享发现根定义，检查默认根、配置根、路径重叠和大小写别名 |
| 安装路径大小写与包父目录拼写 | `.GIT` / `.AGENT` 绕过保留目录检查；跨平台目录结构可能不同 | 保留路径统一比较，包目录拓扑同时要求精确拼写 |
| 上下文写入不预留读取容量 | 到达记录数/字节上限后仍追加，之后整个日志无法恢复 | 预览及锁内都计算新增容量，任何写入之前拒绝超限 |
| 上下文、位置注册、ownership、索引、布局的异常字段 | list/dict 等错误类型造成未处理的 TypeError / KeyError | 在边界校验类型，返回诊断或领域错误；ownership 使用一次有界稳定读取 |
| Skill YAML 使用独立的无界读取/解析路径 | 深层 YAML 导致 RecursionError；元数据读取缺少统一限制 | 复用有界读取和 YAML 图校验，入口文件只读取一次 |
| JSON 缺少结构和有限数检查 | 接受 NaN/Infinity、过深结构，后续摘要/恢复失败 | 限制深度、节点数，并拒绝非有限数 |
| GitHub 元数据永久缓存 | 长期复用 transport 时可能使用过期的仓库公开状态 | 每次描述目标时刷新仓库元数据，重新绑定预览 |
| 上下文已提交后位置注册失败 | 返回失败让调用者误以为上下文未保存 | 返回已保存结果与注册警告，保留按目录恢复能力 |
| 多流重复读取相同证据文件 | 恢复成本随流数量重复放大 | 每个 checkout 的文件只验证一次，总证据读取限制为 64 MiB |
| 导入/安装在等锁期间配置变化 | 可能继续使用旧 inbox 或排除规则 | 锁内重新检查映射、ownership 和安装预览 |

`tests/test_stability_audit.py` 保存复现与回归测试，包括故障注入、锁内配置变化、
容量边界、损坏记录、跨平台路径、YAML/JSON 深度、完整包校验和公开状态刷新。
初始 29 个场景全部失败；随后对旧模块补充的 7 个场景也在修复前失败。
另有测试覆盖中断后的保留行为、可读日志和证据预算耗尽。

## 结构调整

- `skill_package.py` 负责包扫描、编码校验、完整性验证与新目录物化；
  `skill_sync.py` 负责同步流程、来源和隔离边界，删除两份物化/比较实现。
- `sensitive_data.py` 提供共用文本检测，结束同步/上下文模块对 `session` 私有函数的依赖。
- `file_lock.py` 提供 OS 锁原语，四个使用方保留各自的提交、释放和错误处理策略。
- `skill_paths.py` 统一发现根，避免导入隔离与接管发现各维护一套路径定义。
- `io.parse_yaml_safe` 复用现有 YAML 安全契约，避免每个入口重新处理解析限制。

统计范围为 `src/archmarshal/*.py`；包括空行，函数长度按 AST 起止行计算。
依赖图包含延迟相对导入；重复项仅检测超过 8 行且 AST 函数体完全相同的实现，
不代表所有语义重复都能被统计发现。

| 指标 | 审计前 | 修复后 |
| --- | ---: | ---: |
| 顶层 Python 模块 | 42 | 46 |
| 源码行数 | 23,555 | 23,645 |
| 模块依赖环 | 0 | 0 |
| 跨模块私有名称导入 | 14 | 12 |
| 检出的完全重复函数体组 | 1（3 份 OS 加锁实现） | 0 |

体积增加来自必要校验；拆文件本身不等于消除复杂性。主要维护热点仍是：
`user_store.py`（约 3,150 行）、`adoption.py`（约 2,400 行）、
`safety.py`（约 1,970 行）和 CLI 的 753 行分派函数。
建议后续按职责拆分存储格式校验/事务发布、接管发现/计划生成、备份创建/恢复、
CLI 参数注册/命令分派，并在新增功能触及这些区域时逐步替换跨模块私有调用。
本次保留这些既有流程，避免一次性重写已经有恢复语义的代码。

## 验证与边界

Windows / Python 3.11 基线为 423 passed、13 skipped；最终为 **472 passed、13 skipped**，
新增 49 个回归场景。语句覆盖率 **87.43%**、分支覆盖率 **76.15%**；所有既有
模块门槛及新增的 6 项模块门槛通过，没有降低原有门槛。
Ruff、diff 检查、版本一致性、引擎锁、示例项目 lint 均通过。
wheel/sdist 构建和元数据检查通过；两种包均在干净环境安装成功，三个命令入口
及 wheel 的 schema 检查通过；wheel 中 47 个 Python 文件与当前源码逐字节一致。
跨平台 CI 结果见 [PR #1](https://github.com/yptang98/ArchMarshal/pull/1)。

审计检查了生命周期接管与恢复、备份校验与还原、Skill 索引/审查、用户存储、
上下文、同步传输和插件打包路径。既有回归覆盖并发 HEAD 更新、锁替换、
中断恢复、备份篡改、符号链接/Windows junction 和只读诊断。
这不是对所有可能缺陷的证明，也不是独立渗透测试。

明确保留的限制：设备来源是自声明；秘密文本检测是启发式；没有自动执行下载的脚本；
只恢复已记录的交接信息；未完成导入保留为隔离状态，需要人工检查后选择新位置；
日志容量满时拒绝追加，不自动删除历史。文件系统保护针对协作式并发和静态链接，
不承诺抵御同权限进程任意替换祖先目录。GitHub 可见性检查与远端写入之间也不具备
服务端原子条件，不能阻止仓库所有者同时修改可见性。

外部设计参考及取舍见 [portability-references.md](portability-references.md)。
